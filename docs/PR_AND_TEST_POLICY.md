# 《7:55》PR 与自动化测试规范

本文定义《7:55》仓库的变更入口、审查门槛、自动化测试层级和合并规则。目标是让剧情状态、RPG 场景、移动端输入、离线单文件和地图资源在多人开发中保持可验证。

## 1. 适用范围

所有进入 `main` 的变更都通过 Pull Request 完成，包括代码、地图脚本、剧情配置、构建配置和正式文档。紧急修复也使用短分支 PR，通过后再合并。

`main` 始终代表可构建、可演示、可回退的版本。开发者本地目录、聊天附件、ZIP 和未提交素材不能作为后续开发基线。

## 2. 分支与提交

分支命名：

- `feat/<账号>-<主题>`：新增玩法或界面。
- `fix/<账号>-<主题>`：修复缺陷。
- `test/<账号>-<主题>`：测试与质量门槛。
- `docs/<账号>-<主题>`：正式文档。
- `chore/<账号>-<主题>`：构建、依赖和仓库维护。

提交信息采用：

```text
<type>(<scope>): <简短说明>
```

推荐 `type`：`feat`、`fix`、`test`、`docs`、`refactor`、`perf`、`build`、`ci`、`chore`。

提交应围绕单一目的。资源替换、状态迁移、玩法逻辑和大范围排版调整应尽量拆开，便于审查和回退。

## 3. PR 规模与拆分

推荐范围：

- 不超过 20 个文件。
- 代码增删总量不超过 800 行。
- 一个 PR 只修改一个主要玩法闭环或一个基础设施主题。

当变更超过 30 个文件，或增删总量超过 1500 行时，PR 正文必须增加 `## 大型 PR 拆分说明`，说明无法继续拆分的原因、主要模块边界和逐项回退方式。

以下内容通常应拆成独立 PR：

- 地图底图与碰撞坐标更新。
- 存档版本迁移。
- 新章节状态机。
- 浏览器兼容层。
- 音频与大体积素材。
- CI 或依赖体系调整。

## 4. PR 正文契约

每个 PR 必须包含：

- `## 改动`：列出实际改动和明确排除项。
- `## 原因`：说明用户问题、根因或设计目标。
- `## 验证`：列出已运行命令、浏览器路径和结果。
- `## 风险与回滚`：说明状态、存档、坐标、资源体积和回退方式。
- `## 未覆盖`：如实写明没有验证的设备、路径或边界。

涉及玩法状态或存档时，还应写出：

- 进入状态。
- 成功状态。
- 失败状态。
- 重试与重入行为。
- 旧存档迁移行为。

涉及 UI、地图或动画时，`验证` 中至少包含一个桌面视口和一个移动视口。涉及输入时，要分别说明键盘、指针和触控路径。

## 5. 风险分级

### R0 文档与无运行时改动

示例：错别字、说明链接、正式文档补充。

必须通过：

- PR 元数据检查。
- Markdown 人工检查。

### R1 局部 UI 或内容配置

示例：单个手机页面、字幕、剧情 JSON、局部样式。

必须通过：

- PR 元数据检查。
- TypeScript。
- 单元测试。
- 生产构建。
- 对应视口人工检查。

### R2 状态、控制器、场景交互

示例：`src/core`、`src/modules`、Phaser 场景、任务门控、道具消费。

必须通过：

- PR 元数据检查。
- 地图契约。
- TypeScript。
- 单元测试。
- 生产构建。
- 正式单文件构建与离线结构校验。
- 相关章节的浏览器冒烟路径。

### R3 地图、存档、构建与跨运行时改动

示例：地图尺寸或坐标、存档版本、React 与 Phaser 桥、CI、依赖、单文件打包。

必须通过 R2 全部项目，并补充：

- 旧存档迁移样例。
- 主存档损坏后的备份恢复。
- Blink、Gecko、WebKit 至少各一条关键路径。
- `390×844` 移动视口。
- 非 16:9 桌面视口。
- 回退提交或资源哈希。

## 6. 审查与合并

合并前必须满足：

1. 至少一名非作者协作者批准。
2. 所有 review thread 已解决。
3. `PR metadata contract` 通过。
4. `Verify web build` 通过。
5. PR 已同步最新 `main`，且无未说明冲突。
6. PR 正文中的未覆盖项不会阻断当前发布目标。
7. 运行时改动有对应测试，或在正文中说明暂时无法自动化的技术原因和补测任务。

合并方式使用 Squash merge。Squash 提交沿用规范化标题。禁止向 `main` 强制推送，禁止删除 `main`。

合并后发现问题时使用 `git revert` 或 GitHub Revert，保留完整历史。

## 7. 建议的 GitHub 分支保护

仓库所有者应在 `main` 的规则中启用：

- Require a pull request before merging。
- Require 1 approval。
- Dismiss stale approvals when new commits are pushed。
- Require conversation resolution before merging。
- Require status checks to pass。
- Required checks：`PR metadata contract`、`Verify web build`。
- Block force pushes。
- Block deletions。
- Require linear history。
- Include administrators，条件允许时启用。

仓库合并策略建议只保留 Squash merge，关闭 Merge commit。Rebase merge 可按团队习惯保留，但不要与非线性提交策略混用。

## 8. 自动化测试层级

### L0 PR 元数据

由 `.github/workflows/pr-policy.yml` 执行：

- 标题符合 Conventional Commit 形式。
- 正文包含五个必需章节。
- 大型 PR 包含拆分说明。

### L1 静态与资源契约

由 Web CI 执行：

- `npm ci --no-audit --no-fund`
- `npm run map:zijingang`
- `npm run typecheck`
- `git diff --check`

地图契约应覆盖底图尺寸、运行时清单、碰撞遮罩、出生点、入口坐标和人物帧。

### L2 领域逻辑单元测试

由 `npm test` 执行。首批用例使用 Node 22 内置测试运行器和现有 TypeScript 编译器，不增加测试依赖。

当前用例包括：

- 食堂追踪控制器的餐盘识别、点餐、取餐、出口封堵、自行车解锁和追逐结算。
- 食堂阶段错误输入不会推进状态。
- Bike Arcade 里程、换道边界、障碍波可解性和章节结算。
- 第一章、第二章、第三章的功能门控。
- 存档临时 UI 清理、主存档损坏后的备份恢复和存储拒绝。
- 仓库契约，包括 CI 命令、PR 模板和开发者检查点分组。

### L3 构建与离线产物

由 Web CI 执行：

- `npm run build`
- `npm run build:single`
- `npm run build:campus-map-demo`
- `npm run verify:single`
- `npm run verify:campus-map-demo`

校验目标包括内联运行时、内联样式、无外部 HTTP 资源、正式 Demo 与地图 Demo 并存。

### L4 浏览器端到端测试

下一阶段引入 Playwright，并把下列用例设为合并门槛。测试应优先使用 `devCheckpoint` 构造确定状态，完整主线另设每日或发布前任务。

#### E2E-01 新游戏启动

- 打开新存档。
- 关闭 07:55 闹钟。
- 进入手机主页。
- 页面错误和控制台错误为 0。

#### E2E-02 第一章签到闭环

- 使用检查点进入四位数字集齐状态。
- 输入 `0798`。
- 验证错误通知、红闪、黑屏和章节状态写入。
- 第二章不能重新进入已结束的签到操作。

#### E2E-03 第二章移动闭环

- 命名人物。
- 启动体艺记录。
- 取得并组合方向道具。
- 购买并安装手柄。
- 键盘和触控均能让人物移动。

#### E2E-04 图书馆核心闭环

- 读取入口记录。
- 调查 022。
- 并行取得三类恢复材料。
- 完成 CC98 口令。
- 生成 PASS、清退书包、坐到 022。
- 重入图书馆后阶段和材料不回退。

#### E2E-05 食堂双模式闭环

- 从暗色校园沿脚印进入食堂。
- 深色识别三只目标餐盘。
- 浅色归还餐盘。
- 完成点餐和取餐。
- 三次封堵顺序正确推进，错误出口不推进。
- 离开食堂后进入自行车流程。

#### E2E-06 第三章自行车桥

- `chase_ready` 阶段可检查车锁。
- 深色读取编号。
- 浅色使用纸巾清理反光。
- 支付后进入骑行运行时。
- 骑行结束回写 `canteenHunt` 和章节进度。

该用例是第三章发布前的 P0 门槛。当前实现仍需完成场景事件与自行车控制器之间的桥。

#### E2E-07 输入与视口矩阵

视口和内核：

- Blink：`1280×720`、`1440×900`、`390×844`。
- Gecko：`1280×720`。
- WebKit：`1280×720`、`390×844`。

验证：

- 手机框保持 `430×860` 逻辑比例。
- RPG 保持 `960×540` 逻辑比例。
- 无横向文档溢出。
- 虚拟方向键只在粗指针环境出现。
- 键盘、触控和点击寻路都能停止，不残留移动输入。

#### E2E-08 离线单文件

- 直接打开生成的 `demo/index.html`。
- 外部 HTTP 请求为 0。
- 存储不可用时应用仍可启动。
- DEV 检查点不写入正式存档。
- 地图 Demo 不读写正式存档。

#### E2E-09 减弱动态

- 模拟 `prefers-reduced-motion: reduce`。
- 关键反馈仍可识别。
- 永久闪烁、循环缩放和强烈镜头抖动停止或显著减弱。
- 玩法判定与普通模式一致。

## 9. 测试数据与检查点

测试优先使用确定性状态，禁止依赖随机等待或人工拖动坐标猜测。

每个 DEV 检查点应提供：

- 明确的章节和玩法节点。
- 完整的前置道具与状态。
- 正确的运行时、场景和出生点。
- 对应的 `seenChapterIntros`。
- 不写正式存档的会话隔离。

新增流程时，应同时新增入口、关键中间阶段和结果阶段检查点。难度检查点必须写入真实模拟值，例如 `377m` 检查点必须从 377 米开始。

## 10. 失败处理

CI 失败后先判断层级：

- L0：修正标题或 PR 正文。
- L1：修正类型、资源清单、坐标或格式。
- L2：修正状态转移、输入校验或存档迁移。
- L3：修正构建配置、资源引用或单文件输出。
- L4：保留截图、控制台日志、状态快照和触发检查点。

禁止通过删除测试、降低断言、`--no-verify` 或跳过必需工作流来处理失败。若测试暴露既有缺陷，应创建带触发路径的修复任务，并明确它是否阻断当前 PR。
