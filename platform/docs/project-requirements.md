# 2026-10-24 项目文档对应的平台工作边界

依据用户提供的《浙大校园游戏项目｜初步计划与待讨论事项》。游戏本体是核心，平台负责收集、筛选、回应、试玩入口和贡献留痕；不接管剧情控制器、谜题状态、游戏存档或 Godot 资产管线。此文记录软件边界，不替代与负责人确认的预算、人员或上线承诺。

## 首期实现

| 项目要求 | 平台行为 |
|---|---|
| 轻量参与 | 三个清晰入口；正文一句话即可；标题选填 |
| 本章说 | 关联章节、阅读进度过滤、剧透主动加载；当前阅读进度为玩家自设，尚未获得游戏证明 |
| 卡点/操作反馈 | 独立渠道，无需通关，可关联任意公开章节；用设备、操作、卡住位置等提示引导描述 |
| 经历与创意 | 公开收录，不要求策划案；与反馈分流筛选 |
| 件件有回音 | 初始已收录，运营写回复推进状态，原投稿下保留时间线；可试玩/已发布带真实版本和 HTTPS 链接 |
| 不唯点赞论 | 保留点赞、星级评分与排序；状态由有权限的团队成员结合叙事、共鸣和成本推进，不自动按票采纳 |
| 独立账号 | 按用户明确选型使用 Authing，不要求校园 SSO、学号或手机号；文档“独立用户名密码”不再解释为平台自己保存密码 |
| 隐私与署名 | 公开昵称独立设置；匿名投稿不向其他玩家返回原作者编号；改编授权、游戏署名单独选择，保留确认记录 |
| 制作前可撤稿 | 作者自行停止公开；进入过制作后需协商，状态回退不恢复自动撤稿资格 |
| 运营处理 | 服务器指定运营用户 ID；可分渠道、状态、关键词查看，更新进展或隐藏隐私内容；无默认管理员 |
| 传播与域名 | 单条投稿直达链接；预填渠道/章节的入口链接；同源独立部署、HTTPS 和游戏链接配置 |

常规投稿入口链接示例（将域名换成平台实际地址）：

- `/?entry=chapter&chapter=chapter-1`：打开第一章的本章说投稿窗口。
- `/?entry=feedback&chapter=chapter-1`：第一章卡点反馈，不要求通关。
- `/?entry=story&chapter=general`：校园经历分享。
- `/?idea=投稿UUID`：原投稿与处理进度。

游戏侧可以先用普通链接接入上述地址；当前没有修改游戏代码。链接传来的章节只用于选项预填，不能作为通关或身份凭证。

## 本轮没有伪装为已完成的部分

- 真实 Authing 项目、邮件收发、正式域名/主机、微信内跨设备体验需要持有人配置并联调。
- 游戏已玩章节的可信同步需要双方约定进度证明；目前不读取游戏 localStorage，也不把 URL 参数当成通关。
- 没有自动“每日次日必回”承诺、摘要 Bot、消息推送、社群联动或视频发布；由运营团队先人工运行。平台保存处理记录不等于已有人每天处理。
- 没有奖励结算、奖池、抽奖、贡献成就。待运营明确资格、发放与预算规则，再建设可核查的功能，不能用虚构积分/中奖数制造参与感。
- 没有全平台玩家楼中楼讨论、举报流转或专门的撤稿协商工单；本章说当前是按章节组织的一条条留言，运营能在原留言下持续回复。
- 没有把《这一周》这个候选名、五章主线、10月底发布或11月展示写成已确定的产品事实。公开章节目录只是讨论范围，不等于完成或发布。

## 负责人与后续分工

按项目文档，朱兴宇负责平台技术；运营统筹和日常运营人员负责投稿整理、回复、作者授权确认、试玩回访和社群执行。代码通过运营账号权限与处理记录区分这两类工作，不把“已建功能”混同于“运营已落实”。

平台技术任务分为前端交互、后端权限/认证、数据库迁移与数据可见范围、运营处理流程、部署维护五块。每块代码归属见 README，不在游戏或根 npm 中混放。

北化定制以同源代码复用、独立部署与独立数据库为首期边界。当前不是一个多学校共享数据的服务；复制代码时应配置自己的 Authing 应用、数据库、域名、运营账号和校园素材许可，不复用浙大用户池或用户数据。项目预算和负责人贡献口径属于项目管理，不能由软件自动推断或落账。
